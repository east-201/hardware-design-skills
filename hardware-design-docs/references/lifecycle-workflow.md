# 增量维护

## 写入与接管

先用文件名、主题、型号、需求ID和引用检索。已有同义主题则局部修改；没有才用本地创建日新建。技术结果不足以成文时只记录有价值的已知事实/关键TBD；一句“已完成RS485”不能推导出料号与隔离电压。

接管先扫描现有目录、版本与可解析资料；在附录索引链接工程文件。已有文档按主题映射到十二章，逐步迁移，保留有效正文与历史。不要覆盖现有 docs/README；脚本遇无标记README会保留并提示，由Codex把实际索引接入受管块（或手动维护），核对后再同步。不要借整理文档移动EDA原件。

## 修改与冲突

只修改受影响段落与表/图；更新 `updated`，保留 `created`、document_id、首次日期文件名。证据优先看用户明确适用于当前基线的决定与工程版本，再看对应说明及计算，不用“最后修改时间”机械裁决。用户决定和已布板原理图不一致时，区分“目标变更”与“当前实装”，不能把计划写成已实现。

器件/供电/接口变更时沿引用检查：03需求、04架构、05电路、06引脚/电气、07封装/布局、08功率/热、09故障行为、10重验项、12原件/BOM版本。只更新实际受影响处；尚未获得参数就标注预算/布板约束待复核，不计算假数。冲突无法定论则在原处注明并在11章留一条关联问题，继续不依赖该结论的工作。

重要工程变更在01章已有修订记录（不存在且确有变更时才建）记一行：日期、内容/原因、受影响文档和工程文件、重验范围/状态。普通润色不记ECN；不要为一个变更创建多份报告。发布用文档revision、Git提交/标签及简短发布记录，提交/tag等操作按用户授权执行。

## 移动、归档、删除

移动/重命名先查全部入链（含README、图片与参考式链接）；再检查该文档内相对出链，保持ID和创建日，修正路径后全量检查。一般不改首次日期；实质拆分的新主题获得新ID/创建日，原主题注明承接关系。

默认原地把旧方案标为 Obsolete 并注明替代文档/原因，保留历史。确需物理归档时放所属章的 `归档/` 子目录，不增加一级章；README将其列为归档/Obsolete，不算当前设计。更正会误导当前设计的引用，历史引用可保留并标明历史版本。仅用户确需删除时删除，保留必要历史依据；别把删除和归档混为一谈。
